# v0.2.0-rc.1 Pre-RC Integration Audit

Status: **integration freeze candidate**, not a published release.

- Audit date: 2026-08-22
- Release authority repository: `m2selfA/115driver`
- Baseline: published `v0.1.4`
- Planned candidate: `v0.2.0-rc.1`

## Decision

The post-`v0.1.4` work is a minor-version feature release. It introduces broad batch, sync, recovery, MCP, and release-supply-chain capabilities and should not be presented as a patch-only `v0.1.5` scope. The intended first candidate line is therefore `v0.2.0-rc.1`.

R15 already proved the real origin lineage is `latest_published_tag=v0.1.4`, candidate state is `absent`, and a clean temporary repository based on the real `v0.1.4` tag can build a final-version `v0.2.0-rc.1` with six archives, six SPDX SBOMs, twelve checksum entries, host smoke, install smoke, and the compare range `v0.1.4...v0.2.0-rc.1`.

R16 freezes the integration boundary and compatibility story below. It does **not** create a commit, push, tag, draft, attestation, or GitHub release.

## Go library compatibility review

### Restored before freeze

R16 found several response structs whose newer robustness code had unnecessarily changed public layout. The implementation was refactored so validation metadata stays private while the v0.1.4 source layout remains usable:

- `QRCodeStatusResp.Data` is again the v0.1.4 value field. An internal impossible status sentinel distinguishes missing/null JSON data from the valid waiting status without pointerizing the public field.
- `FileStatResponse` again has the v0.1.4 field list and `IsFile StringInt`. Error-envelope and missing/null category checks are performed against the raw response body instead of adding public error fields.
- `OfflineTaskResponse` again contains only `InfoHash` and `Url`. Per-item task acceptance/error fields live in a private wire response used by `AddOfflineTaskURIs`.
- `SharedDownloadInfo` again has the v0.1.4 file metadata layout. Required CDN headers live in the additive `SharedDownloadRequest` type, and CLI/MCP share transfers use `DownloadByShareCodeRequest*`.

`pkg/driver/public_api_compat_test.go` intentionally uses external-package unkeyed literals to pin these compatibility-sensitive v0.1.4 layouts.

### Remaining declaration differences

The final AST declaration scan reports zero removals and only these pre-existing structural differences plus additive APIs:

- `GetFileOption` has an additional **private** `recordOpenTime` field.
- `Pan115Client` has additional **private** request/upload mutexes.
- `ListOptions` has an additional **private** `recordOpenTime` field.
- additive declarations include `WithRecordOpenTime`, `GetRecordOpenTime`, `SharedDownloadRequest`, `DownloadByShareCodeRequest`, and `DownloadByShareCodeRequestWithUA`.

External code could not legally use unkeyed literals for `GetFileOption` or `Pan115Client` because those types already contained private fields. Their private additions therefore do not create a new external unkeyed-literal break.

`ListOptions` is the one known source exception: v0.1.4 had one exported field and could be constructed externally as an unkeyed one-element literal. The added private state makes that form invalid. Keyed literals and the supported option helpers remain valid. This exception is accepted because moving the state to a process-global sidecar would weaken concurrency/replay correctness for read-only `record_open_time=0` handling.

## CLI compatibility review

- Machine inventory found no removed historical command/subcommand `Use` names and no removed historical flag names.
- Existing single-target forms remain supported while batch/source-list forms are additive.
- Search preserves the historical descending default and makes ascending order explicit.
- Destructive/broad operations now fail closed more often (`--dry-run`, `--force`, reviewed plan IDs, budgets). This is an intentional safety tightening, not silent widening of authority.
- Exit codes and JSON envelopes are now explicit and stable. Automation should consume those contracts instead of matching human text.

## MCP compatibility and authority review

All 11 historical MCP tool names remain in source. The major compatibility change is **visibility by capability**, not name removal:

- `get_download_info` was historically always registered; it now requires `--allow-sensitive-tools` because it returns a signed URL to MCP content.
- `download_file` is registered only with a validated `--local-root`; this makes the local-write authority explicit instead of exposing a tool that cannot safely select a filesystem root.
- cloud mutation tools remain behind `--allow-destructive-tools`; local upload also requires `--local-root`.
- old MCP server flags are retained. The legacy `./mcp` main remains buildable and forwards to the shared `internal/mcpapp` implementation, while the release binary uses the stable name `115driver-mcp-server`.

New planning/revalidation/recovery tools deliberately separate read-only review authority from execution authority. Sensitive values such as cookies, receive codes, signed URLs, absolute local roots, hidden object identities, and digests are omitted or redacted from agent-facing results where documented.

## Persisted-state compatibility

### Transfer sessions

Session Store v2 uses schema `115driver.transfer-session`, manifest version 2, and identity schema `115driver.transfer-session-identity/v2`. Valid legacy session payloads are imported only when a managed payload does not already exist. Import is guarded by regular-file/no-symlink checks, source validation, atomic managed copy, destination validation, and cleanup-on-failure; the legacy payload is removed best-effort only after the managed copy is proven usable.

### Sync journals

The sync journal compatibility envelope is frozen as:

- schema identity: `115driver.sync-journal`
- current schema version: `2`
- minimum readable schema version: `1`
- storage layout version: `v1`
- registered migration edge: `v1 -> v2`
- migration source backups: required
- bulk migration marker: crash-recoverable

Legacy v1 journals are therefore readable but are not silently rewritten. The supported migration command records source/target hashes and preserves backups; interrupted bulk migration is reconciled from exact evidence rather than overwritten heuristically.

Machine result contracts keep explicit versioned identifiers including `115driver.sync-journal-list-entry/v1`, `115driver.sync-journal-verification/v1`, `115driver.sync-journal-recovery/v1`, and `115driver.sync-journal-migration-batch-recovery/v1`.

## Configuration and installation compatibility

- Existing config/profile/cookie concepts remain supported.
- `[transfer.sessions]` is additive configuration; defaults are centralized and shared by CLI/MCP.
- Release archives now contain both `115driver` and `115driver-mcp-server` plus README/LICENSE.
- The historical source package `./mcp` still builds. Maintainers should use the named `cmd/115driver-mcp-server` entrypoint for release/install instructions so the executable name is deterministic.
- No manual filesystem move is required for a valid legacy transfer session; let the guarded import path handle it.

## RC integration boundary

The `v0.2.0-rc.1` candidate is intended to include the already-developed post-v0.1.4 vertical slices:

1. multi-target CLI and source-list batch behavior;
2. transfer scheduler/resume/session-store hardening;
3. safe directory sync, persistent journals, verification/recovery, migration, trash/restore, GC, and alias lifecycle repair;
4. share/recycle/offline safety surfaces;
5. expanded MCP read/batch/planning/revalidation/execution/recovery surfaces with typed output schemas and explicit local/sensitive/destructive capability gates;
6. release artifact reproducibility, SBOM, provenance, rerun-safe draft promotion, release lineage preflight, and read-only dry-run certification;
7. the R16 public-source compatibility restorations recorded above.

Unrelated new feature work should not be added to this candidate after the integration freeze without reopening the audit and rerunning the complete release authority.

## R17 commit-ready integration boundary

R17 converted the product freeze above into a dependency-tested commit boundary without modifying Git history in the main worktree. Before adding the boundary checker itself, the exact candidate inventory was 398 paths (98 tracked changes/deletions plus 300 untracked files), of which 380 were Go source/test files. A machine hygiene scan found no untracked binary/cache/temp artifact and no untracked file at or above 1 MiB.

The final boundary, including its own manifest/checker/tests, is 402 paths and is frozen by `V0.2.0_RC1_COMMIT_MANIFEST.json` as a sorted path-set SHA-256 plus five ordered layer hashes:

1. `driver`: 46 paths — `feat(driver): harden API validation and read-only controls`;
2. `core`: 96 paths — `feat(core): add durable transfer and sync recovery engines`;
3. `cli`: 103 paths — `feat(cli): add batch transfer sync and maintenance workflows`;
4. `mcp`: 125 paths — `feat(mcp): add typed batch planning and recovery tools`;
5. `release`: 32 paths — `feat(release): certify reproducible rerun-safe RC promotion`.

The total frozen path-set digest is `3d152170cad105d2e95bcb30a80c2d759dbd48c1c0ca4b3e4a6a998c0c5e3095`. `make verify-rc-commit-boundary` computes the union of `v0.1.4..HEAD`, tracked worktree changes relative to `HEAD`, and untracked Git-visible files, so the same authority applies before, during, and after the five commits are materialized.

R17 tested the ordering in an isolated temporary clone. Each synthetic commit was followed by a fresh `go test -count=1 ./...`. The first meaningful trial showed that three MCP documentation-contract tests depend on README/Makefile/workflow state; those tests were therefore assigned deliberately to the final `release` layer rather than weakening their assertions. With that ownership fixed, all five intermediate commits passed the full Go test suite. A temporary local `v0.2.0-rc.1` tag then rendered exactly the five feature scopes above, and `git diff --name-only v0.1.4..v0.2.0-rc.1` matched the candidate inventory exactly (`missing=0`, `extra=0`). The temporary clone/tag were removed; no commit or tag was created in the main repository.

## R18 reviewed commit materialization authority

R18 adds an index-level review gate without changing the frozen 402-path candidate. No new RC file is introduced: the existing release-layer checker, contract tests, checklist, audit, and README carry the operational hardening, so all R17 path-set counts and hashes remain authoritative.

`release-boundary-check -verify-index-layer <layer>` now compares the Git index against the exact frozen layer count and SHA-256 after first revalidating the complete 402-path candidate. `-verify-index-layer empty` requires a completely unstaged index. For staging, `-print-layer <layer> -print-layer-nul` emits the verified layer as NUL-delimited pathspec data suitable for Git's `--pathspec-from-file` plus `--pathspec-file-nul`, avoiding shell quoting ambiguity. Candidate and staged Git diffs use `--no-renames` so path ownership is expressed as exact repository paths rather than heuristic rename pairs.

The intended materialization loop is therefore: empty-index proof -> NUL pathspec generation -> stage exactly one layer -> exact staged-layer proof -> cached whitespace/stat/summary review -> commit with the frozen subject -> empty-index proof -> full 402-path boundary proof. This authority remains read-only: it does not execute `git add`, `git commit`, `git push`, or tag creation.
The R18 staging rehearsal intentionally keeps `git diff --cached --check` strict. It exposed Markdown hard-break trailing spaces in this audit header, which were removed rather than exempted so every frozen layer can pass the same cached whitespace gate.

## Explicit non-claims and remaining operational gates

- No real `v0.2.0-rc.1` tag or GitHub release has been created by this audit.
- The Windows development checkout is not used to claim a race-detector pass. `release-ready-race` remains an Ubuntu 24.04 CI/release authority.
- Live 115 integration is excluded from the default release gate. Credentialed read-only or destructive integration requires explicit opt-in; destructive cloud integration is not implied by local/CI unit certification.
- The one accepted Go source exception is the external **unkeyed** `ListOptions` literal described above.

## Freeze gates

Before the actual RC tag is allowed:

- `go test ./...`, vet, sync/session repeated certification, release packaging, and cross-build gates must pass on the reviewed commit;
- `make verify-rc-commit-boundary` must match the frozen 402-path total and all five layer hashes before and after commit materialization;
- the manual `release-dry-run` for `v0.2.0-rc.1` must run on that exact commit and report the expected release lineage/state;
- Ubuntu `release-ready-race` must pass;
- final-version GoReleaser/Syft output must verify as 6 archives + 6 SPDX SBOMs + a 12-entry checksum manifest with host/install smoke;
- generated Git-history notes must be reviewed together with [`RELEASE_NOTES_V0.2.0_RC1.md`](RELEASE_NOTES_V0.2.0_RC1.md);
- any compatibility discrepancy discovered after this document is frozen must be recorded and the relevant contract test updated deliberately.
